# Git 分支规则

## 分支名

方法性改动使用：

```text
<类型>/<功能短名>__from_<父分支短名>
```

功能短名限制为 1～3 个词，默认使用小写短横线形式。父分支短名也只保留 1～3 个能识别方法的词，不递归拼接完整祖先名称，也不要求加入哈希。

示例：

```text
feature/adaptive-loss__from_main
feature/temp-schedule__from_adaptive-loss
experiment/hard-negatives__from_adaptive-loss
```

类型约定：

- `feature/`：计划保留或合并的方法改进；
- `experiment/`：探索性方案、消融实验或可能被舍弃的方案；
- `fix/`：修复已有错误；
- `refactor/`：不改变方法逻辑的代码重构。

分支名只表达直接父分支的简短语义。完整祖先关系以 Git 提交图为准。若短名会产生歧义，先询问或使用 `-v2`、`-v3` 等版本后缀，不能覆盖现有分支。

## 分支选择顺序

1. 用户明确指定分支时，使用用户指定的分支。
2. 当前分支不是主分支，且名称与当前功能或方法明显匹配时，直接使用当前分支。
3. 当前位于 `main`、`master` 或仓库默认主分支时，方法性改动创建并切换到 `feature/<短名>__from_main`。
4. 当前位于其他方法分支且用户没有表示其效果不佳时，为下一项方法改进创建新分支。
5. 当前分支用途不清楚、存在无关提交或名称与任务不一致时，先检查并询问。

如果用户自己创建了匹配的分支，不要求重命名，也不强制新建分支。

## 未提交改动

- 混合了当前任务与其他任务的改动：一律先询问。
- 全部改动明确属于当前任务：可以建立保护性 checkpoint，以便安全切换或创建子分支。
- 不使用无区分的 `git add .`；只处理已确认属于当前任务的路径。
- checkpoint 只用于保护工作，不代表合并、推送或发布。

## 效果不佳时

当用户明确指出当前方法效果不佳：

1. 检查当前分支的父分支标识、提交历史和工作区状态；
2. 如果失败分支仅存在本地、未合并、未推送，可以自动删除该分支；
3. 切回原始分支，或从未加入该方法的提交继续修改；
4. 未提交的失败改动可以在确认其全部属于当前任务后回退；
5. 保留实验日志、checkpoint、指标和失败原因。

已推送、已合并、包含唯一结果或无法确定来源的分支不自动删除。涉及强制重置、丢失未保存工作或删除远程引用时先询问。

## 小修改

路径、超参数、数据集适配、多 GPU、日志、配置和不改变方法含义的重构直接在当前分支完成。可以在结果报告中询问是否需要将这些工程性修改同步到历史方法分支，但不自动批量改动历史分支。

# 工作模式路由

## 先做项目侦察

在修改前读取足够的信息来判断范围：目录结构、入口脚本、配置文件、测试或评估脚本、当前分支、`git status`、最近提交、已有 README 和实验记录。读取应围绕当前任务，避免无目的扫描大型数据目录或 checkpoint。

如果项目没有 Git 仓库，记录这一事实并跳过分支操作。如果工作区有未提交改动，先判断它们是否都属于当前任务；无法区分或包含多个任务时先询问。

## 请求分类

### 方法设计

用户要求想创新点、改进方法、优化模型或分析 SOTA 可能性，但没有要求立即修改代码。输出问题建模、候选方案、数学依据、风险、相关文献方向和最小实验计划。

### 方法实现

改动会影响模型机制、优化目标、训练行为或论文科学主张，例如损失函数、采样策略、网络结构、正则化、优化算法和训练流程中的方法性变化。先执行 Git 分支判断，再进行数学分析和实现。

### 工程适配

改动主要涉及路径、超参数、数据集适配、多 GPU、日志、配置、依赖或不改变方法含义的重构。默认在当前分支处理；只有用户另有要求或改动实际改变方法含义时才进入方法分支流程。

### 实验评估与恢复

用户提供实验结果、指出效果变差或要求继续改进时，检查指标、配置、日志和代码版本，判断是方法问题、实验协议问题还是实现问题，再按失败恢复规则行动。

## 需要询问的情况

- 工作区混合了当前任务和其他未提交改动；
- 当前分支名称与任务有一定关联，但用途或基线不清楚；
- 是否属于方法性改动无法从代码和用户描述判断；
- 需要删除已推送、已合并或包含唯一实验记录的分支；
- 需要外部文献检索而用户尚未表达同意或检索范围不明确。

普通实现细节、实验顺序和命名短语可以根据上下文自行决定，不需要为每个小选择询问用户。

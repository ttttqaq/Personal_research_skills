# AI 科研工作模式路由

## 先做项目侦察

在修改代码前读取与当前问题相关的结构、训练和评估入口、配置、已有结果、Git 分支及未提交改动。方法设计时优先了解任务、数据、指标、当前基线和可见失败现象。避免无目的扫描大型数据或 checkpoint。

如果项目没有 Git 仓库，记录这一事实并跳过分支操作。如果工作区有未提交改动，先判断它们是否都属于当前任务；无法区分或包含多个任务时先询问。

## 请求分类

### 方法设计

用户要求想创新点、改进方法、分析性能瓶颈或 SOTA 可能性，但没有要求立即修改代码。先识别错误来源，再从数据、监督、表征、结构、目标、优化、训练、推理和评估等维度挑选相关方向。输出候选方案、经验或理论依据、关键风险和最小验证实验；讨论方案本身不触发分支操作。

### 方法实现

改动可能影响监督信号、模型机制、训练或推理行为、最终能力或论文科学主张。例如改变采样分布、增强策略、预训练任务、模型结构、损失、奖励、优化方法或解码策略。先按 Git 规则判断分支，再选择适合的经验或数学分析并实现。

### 工程适配

改动主要涉及路径、普通超参数调整、数据集接口适配、多 GPU、日志、配置、依赖或不改变方法含义的重构。默认在当前分支处理。若看似工程改动却改变数据分布、训练目标或结果解释，则按方法性改动判断。

### 实验评估与恢复

用户提供实验结果、指出效果变差或要求继续改进时，核对指标、配置、日志、数据版本和代码版本。判断瓶颈属于数据、表征、目标、训练、推理、评估协议还是实现错误，再按失败恢复规则行动。

## 需要询问的情况

- 工作区混合了当前任务和其他未提交改动；
- 当前分支名称与任务有一定关联，但用途或基线不清楚；
- 是否属于方法性改动无法从代码和用户描述判断；
- 需要删除已推送、已合并或包含唯一实验记录的分支；
- 用户希望参考论文，但研究领域或检索范围无法从项目判断。

普通实现细节、实验顺序和命名短语可以根据上下文自行决定，不需要为每个小选择询问用户。
